# Edge function rules

## Contractor publication, funnel and entitlements

- Quote-based appointment-plan checkout resolves annual AI Presence server-side (`annual_presence_decision` + `_shared/annualPresence.ts`) and, when none is valid, adds one tagged one-time CA$350 line to the same session; the webhook grants the 12 months only after verifying that exact undiscounted line, and an SQL overlap trigger refuses a second valid Presence. Why: one combined purchase without ever charging 350 twice or trusting a client flag.

- Both paid 350 entry circuits reject free, unpaid, non-payment and underpaid sessions before paid telemetry or provisioning, using each existing creation contract's taxes. Why: a discounted Checkout can complete without collecting money.
- Invited one-time entry passes no subscription plan to activate_contractor_unified; personalized entry tokens never enter invited provisioning. Why: perpetual subscriptions bypass 12-month expiry/refund and token fallthrough attempts duplicate accounts.

- Contractor public state = generated column `contractors.public_status` (unpublished / published_pending_verification / verified_active = verified + admin_verified); Clara recommendations require verified_active; publishing auto-syncs `contractor_public_pages` via trigger. Payment never sets is_published/is_discoverable (entry 350 skips activate_contractor_unified, which publishes). Why: paid != verified; profile stays private until verification.
- Parcours entrepreneur = 3 étapes + confirmation : /entrepreneur/devis-personnalise (1 entreprise confirmée, 2 objectif annuel + RDV du mois prochain) → /entrepreneur/plan-personnalise/:id (3 entente de départ = plus petit plan couvrant la capacité du mois prochain, prix serveur) → confirmation webhook pricing_status=paid → /pro. Why: première entente rapide, pas forfait maximal.
- The CA$350 12-month Présence IA is resolved only by `contractor_plan_code()` via `annual_presence_status`: the latest still-valid signed LIVE paid period (renewals count, voided by a `deactivated` stripe_webhook row), plus the frozen historical-rights snapshot; renewal is manual. Why: one entitlement source, renewals recognized, no TEST/forged/replay extension.

- `create-checkout-session` LIVE CA$350 entry is released (founder decision 2026-10-29) and no longer checks `entry350TaxCollectionApproved`; other callers (`create-activation-checkout`) still require `ENTRY350_LIVE_CHECKOUT_RELEASED`="true". Why: commercial go-live without weakening auth, tax contract, signed webhook or idempotency.

- Sales-team requests (/directeur-des-ventes): edge `submit-sales-team-request` only, admin-read RLS, idempotency key returns existing row, no outbound message, no offer before review. Why: no fake success, duplicates or public contact exposure.
- Every contractor Stripe checkout (entry 350, Presence + plan, plan) first takes a `reserve_contractor_checkout` reservation (one active per contractor + Stripe mode) and creates Stripe objects with reservation-derived idempotency keys; a superseded open session is expired before a new one, an unrecorded session is expired, never returned; a reservation is released only on Stripe-confirmed expiry or proven non-creation, and a session-less one keeps its key until session expiry + 10 min. Why: the overlap trigger stops duplicate rights only after money is taken, and an unknown Stripe state may still be payable.
- Territory coverage by radius requires property coordinates or one address-level geocode, never a city centroid; exclusions win and the same `territoryVerdict` gates matching and booking. Why: a centroid cannot prove an address is inside a radius.
